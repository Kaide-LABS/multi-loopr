Bring your own agent

multi-loopr runs on the provider access you already pay for. It never proxies or resells a provider's API, and it never asks you to sign into anything of its own — there is no multi-loopr account. This isn't a claim to take on faith: multi-loopr makes zero network calls anywhere in its own source, mechanically enforced by its own boundary scan on every change, not just stated as intent. It never triggers a provider's credential-setup flow either — the one place it touches auth at all is to check whether you're already signed in, the same way doctor reports on the rest of your toolchain. You already have Claude Code and Codex CLI. multi-loopr coordinates them; it doesn't ask you to buy anything else.

So how does the handoff not fall apart?

The obvious worry with two providers on one build: provider A does some work, hands off to provider B, and B either redoes it or ignores it because it never really understood what A did. Two things prevent that. Before any code exists, the plan is interrogated against a six-part stopping test and a human confirms the resulting spec — both providers read that same confirmed spec directly off disk, not a paraphrase of it. Then, what actually crosses the handoff between phases isn't a summary multi-loopr keeps in memory: it's a structured record of git ground truth plus which files were genuinely read and written, hashed to prove it — with an active check that strips out anything resembling the previous provider's own reasoning or conversation, so the next turn inherits the verified result, never an unverified account of it. multi-loopr drive then walks every later phase unattended the same way, deciding after each one from what's actually on disk, not a remembered state. Unattended once running. Human-confirmed before it starts.

The interface is MCP

multi-loopr runs as a Model Context Protocol server. Connect it to any MCP-capable client and it exposes four tools — run, drive, doctor, evidence — so you drive a spec-disciplined, cross-provider build conversationally, from inside your own agent, without hand-writing a config file or leaving the session you're already in. The same four operations are also a plain CLI, if that's what you'd rather script against.

The discipline, before either provider writes anything

Before any code exists, the plan goes through loopr, the spec-discipline layer this tool runs on: an interrogation against a six-part stopping test — does the plan name a real outcome, is it independently checkable, are its edges named, is its boundary confirmed, is there real context worth keeping, are there no unresolved unknowns. A human confirms the resulting spec before anything is built.

The runtime, once building starts

multi-loopr hands each phase between two independently-configured providers: one implements, the other reviews. The reviewer defaults to whichever provider did not write the diff under review, so the check is a second, separate read of the work — not the same model re-reading its own reasoning. Nothing in the core cares which providers those are; each is a thin adapter behind the same interface, which is what makes the reviewer's role real in the first place — the architecture doesn't know or reward one provider agreeing with itself.

An operator can pin either provider to a fixed role instead of the default alternation. An impossible pinning is rejected before any turn runs. A pinning that would force a provider to review its own prior work is surfaced plainly, as a warning, rather than allowed to pass unnoticed.

Wired up today: Claude Code and Codex CLI. That's an adapter count, not an architectural ceiling — adding a third provider is a new adapter behind the existing interface, not a redesign.

What it does today

multi-loopr run

Dispatches one phase's turn sequence between the two configured providers, and mechanically checks that every turn genuinely references the phase's own spec and prior handoff record.

multi-loopr drive

Walks a build through every phase of a target project unattended: after each phase, it decides — from the real state on disk — whether to dispatch the next phase, stop cleanly, or halt on an incoherent state, and logs every decision.

Role pinning

Pin either provider exclusively to the executor role or exclusively to the reviewer role, instead of the default alternation. An impossible pinning is rejected before any turn runs; a pinning that would force self-review is surfaced as a warning, never silently allowed.

multi-loopr evidence

Independently re-derives whether a completed run actually met its own completion criteria, from the run's persisted handoff records, offline — without trusting what the run reported live.

multi-loopr setup

Registers multi-loopr's own MCP server plus two optional research servers (arXiv, paper-search) in one command. Both are optional — nothing about multi-loopr requires them.

How to try it

multi-loopr is MIT-licensed and published on npm. It runs entirely on your own machine, using your own Claude Code and Codex CLI credentials — there is no hosted account and no service multi-loopr operates on your behalf. 

npm install -g multi-loopr
multi-loopr doctor

doctor checks your toolchain and both provider CLIs before you run anything. Full usage is in the README.
